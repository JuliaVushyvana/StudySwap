# Roadmap StudySwap (тижні 1-8)

![[roadmap1.png|Roadmap StudySwap]]

Тижні 1-2 виконані, тижні 3-8 заплановані. Порядок робіт відповідає пріоритетам із `business_doc.md` (спочатку MVP, потім вимоги з позначкою «Пізніше») і темам практичних робіт. **DoD (Definition of Done)** — що має бути готово, щоб вважати тиждень завершеним.

**Правило роботи:** 1 зміна = 1 pull request. У PR має бути опис, скрін або метрика як proof і посилання на тести чи dashboard.

## Тиждень 1. Foundation (виконано)

**Мета:** обрати тему, підняти мінімальну систему й налагодити роботу з Git у команді.

- Тема: **StudySwap**, платформа для обміну навчальними матеріалами між студентами.
- Репозиторій зі структурою `backend/`, `frontend/`, `docs/`; учасники працюють через fork, власні гілки та pull request.
- БД: SQLite, таблиця `items (id, name)` з тестовими рядками (`backend/db.js`, `better-sqlite3`).
- Бекенд: Node.js + Express, endpoint `GET /items`, що повертає дані з БД (`backend/server.js`).
- Клієнт: HTML-сторінка з кнопкою «Load items», яка викликає API й виводить список.

**DoD:** PR #1, #2, #3 змерджені; працює ланцюжок клієнт → бекенд → БД.

## Тиждень 2. Documentation (виконано)

**Мета:** формалізувати ідею проєкту у вигляді документів.

- `docs/business_doc.md`: опис, ролі, матриця доступу, сценарії, нефункціональні вимоги, обмеження.
- Розділ 4 з функціональними вимогами у форматі «Як [роль] хочу...» з AC (Given / When / Then), помилками й кодами відповідей.
- `docs/architecture_diagram.png` і `.drawio`: Client → Backend → Database, модулі за пріоритетом, показники якості.
- `docs/roadmap.md`: цей план.

**DoD:** папка `docs/` у головному репозиторії, усі зміни прийшли через pull request.

## Тиждень 3. Domain + Search

**Мета:** змоделювати предметну область і зробити основну функцію сайту: пошук.

- Практична 3 (DDD): глосарій термінів, піддомени, контекстна діаграма в `docs/domain/`.
- Класи моделей: User, Material, Comment, Report.
- БД: таблиці `users`, `materials`, `comments`, `reports` з тестовими даними (навчальну `items` замінюємо).
- Endpoint `GET /materials`: пошук `q` (до 100 символів), фільтри за університетом, предметом, курсом і типом, сортування `new` / `title`, пагінація `page`.
- Сторінка пошуку та головна сторінка з блоком нових матеріалів.

**Вимоги з розділу 4:** №5, 6, 7.
**DoD:** тести на коди 200 і 400; пошук і фільтри працюють на даних із БД.

## Тиждень 4. API contract + Auth

**Мета:** зафіксувати API документом і закрити вхід до системи.

- Практика 4: ADR про вибір стилю (модульний моноліт), структура `api/`, `service/`, `domain/`.
- `docs/api/openapi.yaml`: CRUD, DTO, єдиний формат помилки; перевірка в Swagger Editor.
- `POST /auth/register`, `POST /auth/login`, `POST /auth/logout`; `GET /health`.
- Паролі лише як bcrypt-хеші, токени JWT, перевірка ролей (`401` без входу, `403` без прав).
- Сторінки реєстрації та входу.

**Вимоги з розділу 4:** №1, 2, 4.
**DoD:** специфікація без помилок у Swagger Editor; мінімум два юніт-тести рівня `service/` (успіх і помилка); коди 400, 401, 409.

## Тиждень 5. Materials CRUD

**Мета:** користувач керує матеріалами.

- `POST /materials` із файлом, `GET /materials/:id`, `DELETE /materials/:id` (власник видаляє свій, адмін будь-який).
- Перевірка типу й розміру файлу (документи до 20 МБ, презентації й архіви до 50 МБ, аудіо до 30 МБ, відео до 100 МБ).
- Практика 5: заголовок `X-Request-Id`, єдиний формат помилки, `Idempotency-Key`, таймаут і ретраї на клієнті.
- Сторінка матеріалу та форма додавання матеріалу.

**Вимоги з розділу 4:** №8, 9, 11.
**DoD:** тести на коди 201, 400, 401, 403, 404; файл поза лімітом дає 400.

## Тиждень 6. Comments + Profiles + Docker

**Мета:** оживити сторінку матеріалу, завершити облікові записи й запакувати проєкт у контейнери.

- Коментарі: `GET` і `POST /materials/:id/comments` (текст 1..1000 символів; читати можуть усі, писати зареєстровані).
- Профіль: `GET /users/me` з аватаркою, нікнеймом і списком матеріалів.
- Скидання пароля: `POST /auth/password-reset`, посилання одноразове й діє не більше 30 хв.
- Практика 6: `Dockerfile` для API й фронтенду, `docker-compose.yml` (web + api + db), інструкція в `README.md`.

**Вимоги з розділу 4:** №3, 10, 12.
**DoD:** `docker compose up -d` піднімає систему; посилання скидання пароля працює один раз.

## Тиждень 7. Reports + CI/CD

**Мета:** порядок на платформі та автоматична перевірка коду.

- `POST /reports` (скарга 1..1000 символів), `GET /reports`, `POST /users/:id/block`.
- Профіль адміна: перегляд скарг, блокування порушників, видалення матеріалів.
- Практична 7: GitHub Actions (`ci.yml`): встановлення залежностей із кешем, тести, лінт; публікація образу в GHCR; бейдж статусу в README.
- Захист гілки `main`: злиття лише при зеленому CI та рев'ю.

**Вимоги з розділу 4:** №13, 14, 15.
**DoD:** зелений CI; 403 для користувачів без прав адміна; червоний CI блокує merge.

## Тиждень 8. Notifications + Observability

**Мета:** зворотний зв'язок для користувачів і прозорість роботи сервісу.

- `GET /notifications`: спливне вікно (нові коментарі, результат розгляду скарги).
- Практична 8: OpenTelemetry → Grafana, логи з `request_id`, дашборд RED, alert при частці 5xx > 1% упродовж 5 хв.
- Навантажувальний тест k6 (100 одночасних користувачів), перевірка відновлення з резервної копії.
- Тестування сценаріїв, фінальні виправлення, підготовка презентації.

**Вимоги з розділу 4:** №16; нефункціональні вимоги: швидкодія, спостережуваність, відновлення.
**DoD:** p95 `GET /materials` ≤ 500 мс; скрін спрацювання alert; restore із копії перевірено.
