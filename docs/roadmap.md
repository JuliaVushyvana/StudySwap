## Тиждень 1. Тема проєкту та базова система (виконано)

**Мета:** обрати тему, підняти мінімальну систему клієнт - бекенд - БД і налагодити роботу з Git у команді.

- Обрано тему: **StudySwap**, платформа для обміну навчальними матеріалами між студентами.
- Лідер створив репозиторій зі структурою `backend/`, `frontend/`, `docs/`; учасники працюють через fork.
- База даних: SQLite, таблиця `items (id, name)` з тестовими рядками (`backend/db.js`, бібліотека `better-sqlite3`).
- Бекенд: сервер на Node.js + Express, endpoint `GET /items`, який повертає дані з БД (`backend/server.js`).
- Клієнт: HTML-сторінка з кнопкою «Load items», що викликає API й виводить список (`frontend/index.html`).
- Git-процес: кожен працює у власній гілці у своєму fork і відкриває pull request у головний репозиторій (PR #1, #2, #3, усі змерджені).

**Результат:** мінімальна робоча система клієнт → бекенд → БД, код у головному репозиторії, команда має тему й початковий код.

## Тиждень 2. Бізнес-документ, архітектурна діаграма, roadmap (виконано)

**Мета:** формалізувати ідею проєкту у вигляді документів.

- `docs/business_doc.md`: опис системи, ролі (гість, користувач, адмін), сценарії, функціональні й нефункціональні вимоги, обмеження.
- `docs/architecture_diagram.drawio` і `.png`: схема Client → Backend → Database, блоки майбутніх модулів (Auth, Users & Profiles, File Storage, Comments, Complaints & Moderation, Notifications, Monitoring), зовнішні сервіси (Email Service, AI Assistant); `docs/architecture.md` пояснює кожен блок словами.
- `docs/roadmap.md`: цей план робіт.
- Усі зміни вносяться через fork і pull request (PR #4 архітектура, PR #5 roadmap).

**Результат:** у репозиторії є папка `docs/` із бізнес-документом, діаграмою та roadmap; команда має спільне бачення системи.

## Тиждень 3. Домен і пошук матеріалів

**Мета:** змоделювати предметну область і зробити основну функцію сайту: пошук.

- Практична 3: виділити піддомени (користувачі, матеріали, модерація), записати глосарій, намалювати контекстну діаграму в `docs/domain/`.
- Класи моделей: User, Material, Subject, University, Comment, Report.
- Розширити БД: таблиці `users`, `universities`, `subjects`, `materials`, `comments`, `reports` з тестовими даними (замість навчальної `items`).
- Новий endpoint `GET /materials`: пошук за назвою, предметом, курсом, університетом і типом; сортування «спочатку нові» та «за назвою (А-Я)».
- Сторінка пошуку: рядок пошуку, фільтри, картки матеріалів, стани «завантаження», «нічого не знайдено», «помилка».

**Результат:** користувач шукає й фільтрує матеріали, дані беруться з БД.

## Тиждень 4. Контракт API та авторизація

**Мета:** зафіксувати API документом і закрити вхід до системи.

- Практика 4: обрати стиль (модульний моноліт), записати рішення в ADR (`docs/adr/`).
- Описати API в `docs/api/openapi.yaml` (CRUD матеріалів, DTO, єдиний формат помилки), перевірити в Swagger Editor.
- Структура коду: `api/`, `service/`, `domain/`; `GET /health`.
- Реєстрація та вхід: `POST /auth/register`, `POST /auth/login` (нікнейм, логін, пароль, пошта, дата народження), вихід.
- Хешування паролів (bcrypt), токени JWT, ролі «Гість», «Користувач», «Адмін», перевірка прав на сервері.
- Сторінки реєстрації та входу.
- Мінімум два юніт-тести рівня `service/`: успішний і помилковий випадки.

**Результат:** працюють реєстрація та вхід, API описане в OpenAPI.

## Тиждень 5. CRUD матеріалів і стійкість API

**Мета:** користувач керує власними матеріалами.

- `POST /materials` із завантаженням файлу, `GET /materials/:id`, `PUT /materials/:id`, `DELETE /materials/:id`.
- Перевірка типу й розміру файлу на сервері за обмеженнями з `business_doc.md`.
- Редагувати й видаляти може власник, адмін видаляє будь-який матеріал.
- Сторінка матеріалу та форма додавання матеріалу (назва, предмет, опис, університет, курс, тип, файл).
- Практика 5: єдиний формат помилки `{ error, code, details, requestId }`, заголовок `X-Request-Id`, ідемпотентність `POST`, таймаут і ретраї на клієнті.
- Головна сторінка з меню, пошуком і блоком нових матеріалів.

**Результат:** користувач додає, переглядає, змінює й видаляє свої матеріали.

## Тиждень 6. Коментарі, профілі, скидання пароля, Docker

**Мета:** оживити сторінку матеріалу, завершити облікові записи й запакувати проєкт у контейнери.

- Коментарі: `POST /materials/:id/comments`, `GET /materials/:id/comments` (читати можуть усі, писати зареєстровані).
- Профіль користувача: аватар, нікнейм, список усіх його матеріалів.
- Скидання пароля через одноразове посилання на пошту (Email Service; на етапі розробки лист можна виводити в консоль або в тестовий SMTP).
- Практика 6: `Dockerfile` для API і фронтенду, `.dockerignore`, `docker-compose.yml` (web + api + db).
- Інструкція запуску з нуля в `README.md`.

**Результат:** коментарі, профілі й скидання пароля працюють, проєкт запускається командою `docker compose up -d`.

## Тиждень 7. Скарги, модерація, CI/CD

**Мета:** порядок на платформі та автоматична перевірка коду.

- Сторінка скарги: дата, хто скаржиться, матеріал і автор, опис, кнопка «Подати». `POST /reports`.
- Профіль адміна: перегляд скарг, блокування порушників, видалення матеріалів. Заблокований користувач не може увійти.
- Практична 7: CI у GitHub Actions (`.github/workflows/ci.yml`): checkout, встановлення залежностей із кешем, тести, лінт.
- Delivery: збірка образу й публікація в GHCR (або артефакт), бейдж статусу CI у README.
- Захист гілки `main`: злиття лише при зеленому CI.

**Результат:** скарги й модерація працюють, кожен pull request автоматично перевіряється.

## Тиждень 8. Сповіщення, моніторинг, доопрацювання

**Мета:** зворотний зв'язок для користувачів і прозорість роботи сервісу.

- Сповіщення: спливне вікно за кнопкою дзвіночка (новий коментар до вашого матеріалу, результат розгляду скарги), лічильник непрочитаних.
- Практична 8: підключити API до OpenTelemetry (трейси та логи), дашборд RED у Grafana, хоча б один алерт на частку помилок.
- Тестування основних сценаріїв, виправлення помилок, підготовка презентації.

**Результат:** працюють сповіщення, стан сервісу видно на дашборді, проєкт готовий до презентації.
