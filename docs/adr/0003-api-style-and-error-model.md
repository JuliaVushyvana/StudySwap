# ADR-0003. Стиль API та модель помилок

## 1. Контекст

- ADR-0001 обрали модульний моноліт, ADR-0002 — шари `api/` → `service/` → `domain/`.
- Контракт `docs/api/openapi.yaml` описує CRUD ресурсу «Матеріал» і `GET /health`. Ним користуються фронтенд (`frontend/index.html`), юніт-тести й рев'ю PR (Pull Reques).
- Без домовленостей кожен роут повертав би помилки по-своєму: десь рядок, десь `{ message }`, десь `500` замість `400`. Фронтенду тоді доведеться розбирати кожен випадок окремо.
- Потрібно зафіксувати: як виглядають URL і методи, у якому форматі повертаються помилки, який статус для якої ситуації і як код тримається у відповідності з OpenAPI.

## 2. Рішення

### Стиль REST

- **Ресурси — іменники в множині**, дія задається методом HTTP: `/materials`, `/materials/{id}`. Дієслів в URL немає (`/materials/create` заборонено).
- **Методи:**

| Метод | Шлях | Що робить | Успіх |
|---|---|---|---|
| `GET` | `/materials` | список з пошуком `q`, фільтрами (`subject`, `university`, `course`, `type`), `sort`, `page` | `200` `MaterialListResponse` |
| `POST` | `/materials` | створити матеріал | `201` `MaterialResponse` |
| `GET` | `/materials/{id}` | деталі матеріалу | `200` `MaterialResponse` |
| `PATCH` | `/materials/{id}` | часткове оновлення (лише передані поля) | `200` `MaterialResponse` |
| `DELETE` | `/materials/{id}` | видалити (м'яко: статус `deleted`) | `204` без тіла |
| `GET` | `/health` | перевірка, що сервер живий | `200` `text/plain` `ok` |

- **`PATCH`, а не `PUT`.** Клієнт змінює одне-два поля, а файл матеріалу змінювати не можна, тож повна заміна ресурсу (`PUT`) не потрібна. `PUT` не реалізуємо.
- **JSON у тілі й відповіді**, поля в `camelCase` (`fileId`, `authorNickname`, `createdAt`). Дати — рядки ISO 8601 в UTC.
- **Список — завжди об'єкт** `{ items, total, page }`, а не голий масив: так можна додати поля пагінації, не ламаючи клієнтів. Розмір сторінки — 20. Порожній результат — `200` з `items: []`, а не `404`.
- **Автор береться з токена**, а не з тіла запиту. Внутрішні поля (`status`) у відповідь не потрапляють: між доменом і HTTP завжди стоїть DTO (`service/catalog/materialDto.js`).
- **Невідомі поля в тілі відхиляються** (`additionalProperties: false` → `400 UNKNOWN_FIELD`), щоб помилка в назві поля не губилася мовчки.
- **Версіонування** поки не потрібне: клієнт один і живе в тому самому репозиторії. Коли контракт доведеться ламати, додамо префікс `/v2`.

### Формат помилки

Усі помилки всіх ендпоїнтів — єдиний `ErrorResponse`:

```json
{
  "error": "ValidationError",
  "code": "TITLE_REQUIRED",
  "details": [{ "field": "title", "message": "Назва обов'язкова" }],
  "requestId": "3f2a9c1e-7b44-4d0e-9a51-0c2f6e8d1b77"
}
```

| Поле | Значення |
|---|---|
| `error` | категорія, однозначно задає HTTP-статус: `ValidationError`, `Unauthorized`, `Forbidden`, `NotFound`, `InternalError` |
| `code` | конкретна причина у `UPPER_SNAKE_CASE` для програмної обробки на фронтенді; `null`, якщо уточнення немає |
| `details` | для валідації — усі знайдені помилки полів `[{ field, message }]`, щоб форма підсвітила їх одразу; інакше `null` |
| `requestId` | той самий id, що в заголовку `X-Request-Id`; за ним шукаємо запит у логах |

Як це влаштовано в коді:

- `service/` кидає класи з `service/errors.js` (`ValidationError`, `UnauthorizedError`, `ForbiddenError`, `NotFoundError`) і нічого не знає про HTTP-статуси.
- `api/middleware/errorHandler.js` — **єдине місце**, яке перетворює помилку на статус і `ErrorResponse`. Роути помилок не ловлять (Express 5 сам передає винятки в обробник).
- `api/middleware/requestId.js` призначає `requestId` кожному запиту.
- Невідома помилка → `500 InternalError` без деталей: стек і повідомлення пишемо лише в лог з `requestId`, клієнту не віддаємо.
- `message` у `details` — українською для користувача; фронтенд орієнтується на `code`, а не на текст.

### Політика кодів

| Статус | `error` | Коли | Приклади `code` |
|---|---|---|---|
| `200` | — | успішне читання або оновлення | — |
| `201` | — | ресурс створено, у тілі — створений ресурс | — |
| `204` | — | успішне видалення, тіла немає | — |
| `400` | `ValidationError` | дані не відповідають контракту: тіло, query-параметри, некоректний JSON | `TITLE_REQUIRED`, `TITLE_TOO_LONG`, `COURSE_OUT_OF_RANGE`, `INVALID_TYPE`, `FILE_REQUIRED`, `EMPTY_UPDATE`, `UNKNOWN_FIELD`, `INVALID_JSON`, `INVALID_PAGE` |
| `401` | `Unauthorized` | дія потребує входу, а токена немає або він недійсний | `UNAUTHORIZED` |
| `403` | `Forbidden` | користувач відомий, але прав немає (не автор і не адмін) | `FORBIDDEN` |
| `404` | `NotFound` | ресурсу немає, він видалений, або такого маршруту немає | `MATERIAL_NOT_FOUND`, `ROUTE_NOT_FOUND` |
| `409` | `Conflict` | конфлікт зі станом системи; з'явиться з `POST /auth/register` (email уже зайнятий) | `EMAIL_TAKEN` |
| `500` | `InternalError` | непередбачена помилка сервера | `null` |

Правила, які прибирають неоднозначність:

- **Порядок перевірок** у use-case: `401` → `404` → `403` → `400`. Гість не дізнається, чи існує матеріал; чужий матеріал не валідуємо, а одразу відмовляємо.
- **Видалений матеріал — `404`**, а не `410` чи `403`: для клієнта його просто немає.
- **Некоректний `id` у шляху** (`/materials/abc`) — `404 MATERIAL_NOT_FOUND`: такого ресурсу не може існувати, окремий код клієнту нічого не дає.
- **Непідтримуваний метод чи шлях** (`PUT /materials/1`) — `404 ROUTE_NOT_FOUND`. `405` поки не вводимо, бо клієнт один і використовує лише описані в контракті методи.
- **`400` замість `422`.** Розділяти «синтаксично неправильно» і «семантично неправильно» поки нема потреби: обидва випадки — `ValidationError`, а різницю видно з `code`.
- Новий `code` додається одночасно в код і в опис `ErrorResponse` в `openapi.yaml`.

### Відповідність OpenAPI

- **`docs/api/openapi.yaml` — джерело правди.** Спершу змінюємо контракт, потім код (contract-first). PR, що змінює поведінку API без зміни `openapi.yaml`, не приймається.
- Контракт перевіряється в Swagger Editor без помилок (DoD тижня 4).
- DTO-валідація в `service/<модуль>/*Dto.js` повторює схеми контракту: обов'язкові поля, межі (`maxLength`, `minimum`/`maximum`), `enum`, `additionalProperties: false`. Межі беруться з констант домену (`TITLE_MAX`, `COURSE_MAX`), щоб не розійтися з інваріантами `Material`.
- Відповіді будуються лише через `toResponse()` — він повертає рівно поля зі схеми `MaterialResponse`.
- Юніт-тести `backend/test/` перевіряють, що успішна відповідь має поля схеми, а помилки — потрібний клас і `code`.
- На рев'ю PR перевіряємо: новий ендпоїнт є в `openapi.yaml`, статуси відповідей збігаються з описаними, нові `code` внесено в список.

## 3. Альтернативи

### Різний формат помилок у різних роутах — відхилено

Найпростіше на старті (`res.status(400).send('bad title')`), але фронтенд мусив би знати формат кожного ендпоїнту, а `requestId` для пошуку в логах губився б.

### RFC 9457 (Problem Details, `application/problem+json`) — відхилено поки що

Стандартний формат з полями `type`, `title`, `status`, `detail`. Він гарний для публічних API, але для одного внутрішнього клієнта його поля (`type` як URI) — зайва церемонія. Наш `ErrorResponse` легко перевести на Problem Details пізніше: `error` → `title`, `code` → розширення, `details` → `errors`.

### Code-first (генерувати OpenAPI з коду) — відхилено

Документ з'являвся б після коду, і фронтенд не міг би починати роботу паралельно. Крім того, генератори для Express потребують анотацій у кожному роуті, що суперечить тонким роутам з ADR-0002.

### `PUT` для оновлення — відхилено

Вимагає передавати весь ресурс, разом із полями, які змінювати не можна (`fileId`, `authorId`). `PATCH` з `minProperties: 1` точніше описує сценарій «виправити назву чи курс».

## 4. Наслідки

### Для розробки

- Фронтенд обробляє будь-яку помилку одним кодом: дивиться `error`/`code`, а поля з `details` підсвічує у формі.
- Сервіс не знає про HTTP, статус призначається в одному місці — `errorHandler.js`. Новий тип помилки = клас у `service/errors.js` + рядок у таблиці `STATUS`.
- За `requestId` з відповіді можна знайти запит у логах, а пізніше — у Grafana (тиждень 8).
- Валідацію фактично описано двічі: у `openapi.yaml` і в `materialDto.js`. Розходження ловимо тестами й на рев'ю; автоматичну перевірку відповідей за схемою (наприклад, `express-openapi-validator` або контрактні тести) можна додати разом із CI на тижні 7.

### Для релізів

- Будь-яка зміна API починається з PR у `openapi.yaml`, тож ламаючі зміни видно заздалегідь.
- Додати поле у відповідь безпечно; перейменувати чи прибрати поле або змінити статус — ламаюча зміна, яка потребує узгодження з фронтендом (а з часом — версії `/v2`).
