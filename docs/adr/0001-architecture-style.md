# ADR-0001. Стиль архітектури: модульний моноліт

## 1. Контекст

### Стан проєкту

- Виконано тижні 1-3 roadmap. Працює ланцюжок клієнт → бекенд → БД: Express-сервер з одним endpoint `GET /items` і база SQLite.
- Є бізнес-документ, архітектурна діаграма, roadmap і доменна модель: 8 контекстів (`access`, `profiles`, `catalog`, `storage`, `discussion`, `moderation`, `notifications`, `assistant`), прототипи сутностей лежать у `backend/domain/`.
- Контексти тісно пов'язані: матеріал має автора, файл, коментарі й скарги, а сторінка пошуку збирає дані з кількох контекстів в одній відповіді.
- Навантаження невелике: до 100 одночасних користувачів, ціль p95 `GET /materials` ≤ 500 мс (`docs/business_doc.md`).
- Попереду MVP (пошук, авторизація, CRUD матеріалів, коментарі, профілі), потім Docker, CI/CD і моніторинг.

### Процеси

- Один репозиторій на GitHub.
- Робота через fork - власна гілка - pull request з рев'ю; 1 зміна = 1 PR.
- Автотестів і CI поки немає (заплановані на тижні 4 і 7).
- Реліз — запуск одного застосунку: зараз локально, з тижня 6 у Docker.

## 2. Рішення

Обираємо **модульний моноліт** (варіант А).

- Один застосунок Node.js + Express, одна БД SQLite, одне розгортання.
- Код поділено на модулі за контекстами з доменної моделі.
- Модулі спілкуються лише через публічний інтерфейс (`service/` модуля). Заборонено імпортувати чужі внутрішні файли й читати або змінювати чужі таблиці.
- Усередині модуля шари `api/` → `service/` → `domain/`.
- Спільні речі (перевірка JWT і ролей, валідація, формат помилки) робимо один раз для всього застосунку.

### Чому саме так

**Основні сценарії StudySwap зачіпають кілька контекстів одночасно.**

- *Пошук матеріалів* (`GET /materials`). Кожна картка в результатах містить назву й предмет (`catalog`), нікнейм автора (`profiles`), тип і розмір файлу (`storage`) та кількість коментарів (`discussion`). У моноліті `catalog` отримує ці дані через виклики `service/` інших модулів у тому самому процесі: це частки мілісекунди, і такий виклик не може «не дійти». У мікросервісах `catalog` мав би на кожен пошук робити ще 3 HTTP-запити до інших сервісів. Кожен із них додає затримку до цілі p95 ≤ 500 мс і може не відповісти, а тоді сторінка пошуку не відкриється.
- *Видалення матеріалу адміном після скарги.* Треба приховати матеріал (`catalog`), видалити файл (`storage`), закрити скарги (`moderation`) і повідомити автора (`notifications`). У моноліті перші три кроки виконуються в одній транзакції SQLite: або все, або нічого. У мікросервісах це запити до 4 сервісів, і якщо один упаде посередині, лишиться, наприклад, видалений матеріал з відкритими скаргами або файл без матеріалу. Таке доведеться відстежувати й виправляти вручну.
- *Реєстрація.* Створюються обліковий запис (`access`) і профіль (`profiles`). У моноліті це одна транзакція, у мікросервісах — два сервіси, між якими може з'явитися користувач без профілю.

**Інфраструктуру для кожного сервісу довелося б робити тим самим двом людям.** За roadmap на тижні 6-8 ми додаємо Docker, CI і моніторинг. Для моноліту це один `Dockerfile`, один пайплайн GitHub Actions і один сервіс у Grafana. Для мікросервісів усе це множиться на кількість сервісів, а ще знадобляться API gateway або CORS, перевірка JWT у кожному сервісі й налаштування зв'язку між ними. Ці тижні ми б витратили на інфраструктуру, а не на коментарі, профілі й скарги з MVP.

**Мікросервіси не вирішили б жодної нашої проблеми.** До 100 одночасних користувачів обслуговує один процес Node.js. Жоден модуль не має окремого навантаження, яке треба масштабувати окремо. Релізимо ми все разом, і в кожному модулі працюють обидва розробники.

**Модулі зберігають можливість винести частину пізніше.** Найслабше пов'язані з рештою `assistant` (звертається до зовнішнього AI API, пізніше може знадобитися Python) і `notifications` (надсилає листи, повільні й ненадійні SMTP-виклики). Поки інші модулі викликають їх лише через `service/`, винесення в окремий сервіс означає замінити виклик функції на HTTP-клієнт в одному місці, не переписуючи `catalog`, `moderation` чи `access`.

## 3. Альтернативи

### Пілот мікросервісів (варіант Б) — відхилено

Що це означало б: винести один контекст (наприклад, `catalog`) в окремий сервіс зі своїм API, даними й деплоєм.

- **За:** сервіси можна розгортати й масштабувати окремо; збій одного не кладе інші; межі контекстів важко порушити.
- **Проти** (з огляду на лекцію 4): виклики між частинами системи стають HTTP-запитами, а отже:
  - запит може залишитися без відповіді, тож потрібні таймаути й повторні спроби;
  - після втраченої відповіді повторний `POST` може створити дублікат, тож потрібна ідемпотентність;
  - послідовні запити між сервісами додають затримку, і ціль p95 ≤ 500 мс тримати важче;
  - кожна межа вимагає окремого контракту API, а перевірку JWT і ролей треба робити в кожному сервісі;
  - сервіси на різних адресах потребують налаштування CORS або API gateway.
- Крім того: дані розділені між сервісами (немає спільних транзакцій і JOIN), а кожен сервіс потребує окремого запуску, Docker-образу й CI.

### Звичайний моноліт без модулів — відхилено

Один застосунок без внутрішніх меж. Простіше на старті, але межі контекстів швидко розмиваються, код переплітається, і пізніше нічого не вдасться винести окремо.

## 4. Наслідки

### Для розробки

-  Простий запуск: `npm install` і `npm start`, одна база.
- Модулі викликають одне одного як звичайні функції, без мережевих помилок; транзакції працюють у межах однієї БД.
-  Легко писати юніт-тести рівня `service/` і налагоджувати код.
-  Межі модулів тримаються на домовленостях, тому кожен PR треба перевіряти на рев'ю, щоб ніхто не імпортував чужі файли й не лазив у чужі таблиці.
-  Усі модулі пишуться однією мовою й на одних версіях бібліотек.

### Для релізів

-  Один застосунок, один Docker-образ, один CI-пайплайн, одне місце для моніторингу.
-  Будь-яка зміна, навіть в одному модулі, вимагає перевірки й розгортання всього застосунку.
-  Масштабувати можна лише весь застосунок цілком; збій одного модуля може зачепити весь сервер.
