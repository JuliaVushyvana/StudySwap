# ADR-0002. Шарова архітектура бекенду

## 1. Контекст

- ADR-0001 обрали модульний моноліт: модулі за контекстами (`access`, `catalog`, `storage` тощо), які спілкуються лише через публічний інтерфейс. 
- На тижні 4 з'являється перший справжній CRUD (`/materials` з `docs/api/openapi.yaml`) і перші юніт-тести. До цього весь код лежав у `server.js`: роут сам робив SQL-запит до БД.
- Потрібно домовитися, де лежить який код, щоб обидва розробники клали його в одні й ті самі місця, а логіку можна було тестувати без HTTP і без БД.

## 2. Рішення

Бекенд ділиться на три шари. Усередині кожного шару — папки модулів.

```
backend/
├── api/                    шар 1: HTTP
│   ├── middleware/         requestId, auth, errorHandler (спільні для всіх модулів)
│   ├── catalog/            materialsRouter.js
│   └── health/             healthRouter.js
├── service/                шар 2: use-case-и
│   ├── errors.js           ValidationError, UnauthorizedError, ForbiddenError, NotFoundError
│   ├── access/             accessService.js, userRepository.js
│   ├── catalog/            materialService.js, materialDto.js, materialRepository.js
│   └── storage/            storageService.js, fileRepository.js
├── domain/                 шар 3: сутності та інваріанти
│   ├── access/User.js
│   ├── catalog/Material.js
│   └── storage/StoredFile.js ...
├── app.js                  збирає застосунок: створює репозиторії, сервіси й роути
├── db.js                   підключення до SQLite
└── server.js               запуск сервера
```

### Що лежить у кожному шарі

| Шар | Що тут | Приклад у StudySwap |
|---|---|---|
| `api/` | Роути й middleware. Беруть дані із запиту (`params`, `query`, `body`, токен), викликають сервіс і віддають відповідь із потрібним статусом. Помилки перетворюють на `ErrorResponse`. Жодних рішень «чи можна» і жодного SQL. | `materialsRouter.js`: `POST /` → `materialService.create(req.user, req.body)` → `201` |
| `service/` | Use-case-и: перевірка вхідних даних за контрактом (DTO), перевірка прав, виклик доменних методів, збереження через репозиторій, мапінг domain ↔ DTO. Репозиторії модуля (весь SQL) теж тут. | `materialService.update`: 401 → 404 → 403 → валідація → `material.update()` → `repository.update()` |
| `domain/` | Сутності та їхні інваріанти: правила, які мають виконуватися завжди, незалежно від того, звідки прийшов виклик. Чистий JavaScript без Express, SQL і HTTP-статусів. | `Material`: назва 1..200, курс 1..6, редагувати може автор або адмін, видалений матеріал не можна змінити |

### Напрямок залежностей

Лише згори вниз:

```
api/  ──►  service/  ──►  domain/
```

- `api/` імпортує `service/` (сервіси й `service/errors.js`).
- `service/` імпортує `domain/` і отримує підключення до БД через фабрику репозиторію.
- `domain/` не імпортує нічого з проєкту, крім інших файлів `domain/`.
- Залежності між модулями — тільки на рівні `service/` і тільки через публічний сервіс модуля: `materialService` отримує `storageService` (а не `fileRepository`) і питає `storageService.getFile(fileId)`.
- Усі залежності передаються в сервіс параметрами фабрики (`createMaterialService({ materialRepository, storageService })`), а створюються в одному місці — `app.js`. Тому в тестах їх можна замінити фейками.

### Заборонені зв'язки

| Заборонено | Чому | Як правильно |
|---|---|---|
| `api/` звертається до БД (`db.prepare(...)`) або до репозиторію | роут перестає бути тонким, а логіку не протестувати без HTTP | роут викликає метод сервісу |
| Бізнес-логіка в `api/` (перевірка прав, валідація полів, підрахунок сторінок) | правила розмазуються по роутах і дублюються | усе це в `service/` |
| `domain/` імпортує Express, `better-sqlite3`, `service/` або `api/` | домен має працювати однаково в тестах, у `demo.js` і в застосунку | домен кидає помилки, а сервіс вирішує, який це HTTP-статус |
| `service/` повертає або приймає `req`/`res` чи знає про HTTP-статуси | сервіс тоді не викликати з тестів чи з іншого модуля | сервіс приймає звичайні дані й кидає помилки з `service/errors.js`, а статус призначає `api/middleware/errorHandler.js` |
| Модуль імпортує репозиторій або читає таблицю іншого модуля | порушує межі з ADR-0001 | виклик публічного сервісу модуля-власника |
| Репозиторій повертає рядки БД назовні | структура таблиці «протікає» в інші шари | репозиторій повертає доменні об'єкти (`Material`, `User`) |
| Імпорт угору (`service/` → `api/`, `domain/` → `service/`) | з'являються цикли, шари не розділити | залежності лише згори вниз |

## 3. Альтернативи

### Модуль зверху, шари всередині (`backend/catalog/api|service|domain`) — відхилено

Межі модуля видно краще, але прототипи сутностей уже лежать у `backend/domain/<контекст>/` (Практика 3), і на них спираються `domain/index.js` і `demo.js`. Розкладка «шар зверху» збігається зі структурою з практикуму (`api/`, `service/`, `domain/`) і не вимагає переносити вже написаний код. Межі модулів тримаються тим, що в кожному шарі є папка модуля.

### Окремий шар `repository/` (або `data/`) — відхилено поки що

Чотири шари дали б більше церемоній без реальної користі: у кожного модуля поки по одному репозиторію. Репозиторій лежить у `service/<модуль>/` поруч із сервісом, який його використовує. Якщо з'явиться складна робота з даними (кілька БД, кеш), винесемо репозиторії в окремий шар.

## 4. Наслідки

### Для розробки

-  Роути короткі: одна-дві стрічки на ендпоїнт.
-  Сервіс тестується юніт-тестами з фейковим репозиторієм і сховищем, без БД і без запуску сервера (`npm test`).
-  Інваріанти `Material` перевіряються один раз у домені й діють і при створенні, і при оновленні.
-  Більше файлів: на один ресурс — роут, сервіс, DTO, репозиторій, сутність.
-  Правила залежностей поки що перевіряються лише на рев'ю PR. Автоматичну перевірку (лінтер з забороною імпортів) можна додати разом із CI на тижні 7.

### Для релізів

-  Зміни в контракті API зачіпають переважно `materialDto.js` і роут, а не доменну модель.
-  Новий ресурс вимагає змін у трьох шарах і в `app.js`, тож PR виходять більшими.
