# ADR-0004. Обробка збоїв: ідемпотентність, ретраї, таймаути, degraded mode

## 1. Контекст

- ADR-0003 зафіксував єдиний `ErrorResponse` і політику кодів для «нормальних» помилок: валідація, права, відсутній ресурс.
- Практика 5 (тиждень 5 `docs/roadmap.md`) — помилки, які виникають не через клієнта, а через мережу й навантаження: відповідь загубилася, сервер повільний, БД недоступна, клієнт шле забагато запитів.
- Найбільш вразливі місця StudySwap:
  - **`POST /materials`.** Студент натискає «Опублікувати», відповідь губиться (Wi-Fi у гуртожитку, таймаут), клієнт повторює запит — і в каталозі з'являються два однакові конспекти.
  - **Пошук `GET /materials`** — головна сторінка. Якщо БД на мить недоступна (файл SQLite заблоковано, диск переповнено), користувач бачить порожню сторінку замість каталогу.
  - **Повільна відповідь.** Без таймауту клієнт чекає без кінця, а з'єднання займають ресурси сервера.
  - **Шквал запитів** (ретраї без паузи, скрипт, баг у фронтенді) перевантажує один процес Node.js, який обслуговує всіх (ADR-0001).
- Ретраї роблять клієнт стійкішим, але без правил на сервері вони лише посилюють проблему: дублікати й ще більше навантаження.

## 2. Рішення

### `X-Request-Id` — наскрізний ідентифікатор запиту

- `api/middleware/requestId.js`: береться із заголовка клієнта (до 128 символів) або генерується UUID.
- Повертається в заголовку відповіді **завжди** і в полі `requestId` кожної помилки, а також пишеться в лог.
- Клієнт **використовує той самий `X-Request-Id` для всіх ретраїв** однієї операції, тож у логах видно всю історію спроб.
- CORS віддає браузеру `X-Request-Id` і `Retry-After` (`exposedHeaders`), інакше фронтенд не прочитає їх.

### Ідемпотентність `POST /materials`

- Заголовок `Idempotency-Key` **обов'язковий** (`400 IDEMPOTENCY_KEY_REQUIRED`). Клієнт генерує UUID один раз на дію користувача (натискання «Опублікувати») і повторює його в кожному ретраї.
- `service/idempotency/idempotencyService.js` виконує use-case один раз для пари (користувач, ключ) і зберігає результат у таблиці `idempotency_keys` на 24 години:

| Ситуація | Відповідь |
|---|---|
| новий ключ | use-case виконується, `201`, результат зберігається |
| той самий ключ і те саме тіло | `201` з **тим самим** матеріалом, нового не створено |
| той самий ключ, інше тіло | `409 IDEMPOTENCY_KEY_REUSED` (клієнт переплутав ключі) |
| use-case кинув помилку (`400`, `401`…) | нічого не зберігається, виправлений запит можна надіслати з тим самим ключем |
| минуло 24 год | ключ вважається новим |

- Ключі зберігаються в SQLite, а не в `Map`: після перезапуску сервера ретрай не створить дубліката.
- Ключ прив'язаний до користувача: однаковий UUID у двох людей не конфліктує, і чужий результат не віддається.
- Тіло порівнюється за SHA-256 канонічного JSON (порядок полів не важливий).
- Гонки двох одночасних однакових запитів немає: `better-sqlite3` синхронний, а Node виконує use-case від перевірки ключа до запису без перемикань.
- `GET`, `PATCH`, `DELETE` ідемпотентні за своєю природою (повторний `PATCH` з тими самими полями дає той самий стан, повторний `DELETE` → `404`), тому ключ для них не потрібен.

### Таймаути

- **Серверний:** `api/middleware/timeout.js`. Якщо відповідь не готова за `REQUEST_TIMEOUT_MS` (5 с за замовчуванням) → `503 REQUEST_TIMEOUT` з `Retry-After: 1`. Обробник, який завершиться пізніше, уже нічого не надсилає (`req.timedOut`, перевірка `headersSent` в `errorHandler`).
- `server.requestTimeout` (2× таймаут обробки) обриває з'єднання, які надто повільно надсилають сам запит.
- **Клієнтський** (фронтенд, окрема задача): `AbortController` з таймаутом ~3 с для `GET` і ~5 с для `POST` — менше за серверний, щоб користувач не чекав марно.

### Ретраї та `Retry-After`

Сервер підказує, **чи** і **коли** повторювати, а клієнт виконує ретраї:

| Відповідь | Повторювати? | Коли |
|---|---|---|
| `429 RATE_LIMITED` | так | не раніше, ніж через `Retry-After` |
| `503` (`REQUEST_TIMEOUT`, `CATALOG_UNAVAILABLE`, `SERVICE_UNAVAILABLE`) | так | через `Retry-After` |
| `500`, мережева помилка, клієнтський таймаут | так | експоненційна пауза з jitter: ~0.5 с, 1 с, 2 с |
| `400`, `401`, `403`, `404`, `409` | **ні** | помилка клієнта, повтор дасть те саме |

- Максимум 3 спроби. `POST` повторюється лише з тим самим `Idempotency-Key`.
- Jitter (випадкова добавка до паузи) потрібен, щоб клієнти, які впали одночасно, не повернулися теж одночасно.

### Rate limit

- `api/middleware/rateLimit.js`: фіксоване вікно на IP-адресу, `RATE_LIMIT_MAX` запитів (50) за `RATE_LIMIT_WINDOW_MS` (10 с). Понад ліміт → `429 RATE_LIMITED` з `Retry-After` до кінця вікна.
- IP береться з `req.ip`, а не напряму з `X-Forwarded-For`: інакше клієнт обійде ліміт, підставивши будь-який заголовок. Коли з'явиться reverse proxy (Docker, тиждень 6), увімкнемо `trust proxy`.
- Лічильники в пам'яті процесу. Для одного інстансу цього досить (ADR-0001); якщо інстансів стане кілька, лічильник доведеться винести (наприклад, у Redis).
- `/health` не обмежується, щоб моніторинг не отримав `429` замість справжнього стану.

### Degraded mode

- **Каталог.** `materialService` тримає останню успішно прочитану копію опублікованих матеріалів. Якщо БД недоступна, `GET /materials` шукає по цій копії і повертає `200` з `degraded: true` (фронтенд показує банер «дані можуть бути застарілими»). Якщо копії ще немає → `503 CATALOG_UNAVAILABLE` з `Retry-After: 5`.
- Запис (`POST`, `PATCH`, `DELETE`) у degraded mode не імітуємо: краще чесна помилка, ніж матеріал, який «зник» після відновлення БД.
- **`GET /health`** перевіряє кожну залежність (`database`: `SELECT 1`) і повертає `200 { status: "ok" }` або `503 { status: "degraded", checks: { database: "fail" } }`. Це readiness-сигнал для Docker healthcheck і моніторингу (тиждень 8).

### Штучні збої для перевірки (`CHAOS=1`)

- `api/middleware/faultInjection.js` вмикається лише змінною `CHAOS=1`: 15 % запитів затримуються на 1.2–2 с, 20 % завершуються `503 SERVICE_UNAVAILABLE` або `500`.
- Так можна перевірити клієнтські таймаути, ретраї, `Retry-After` і degraded UI без справжньої аварії. `/health` штучно не ламається.

### Єдиний формат помилки

Усі нові відповіді — той самий `ErrorResponse` з ADR-0003; додано категорії й коди:

| Статус | `error` | `code` |
|---|---|---|
| `400` | `ValidationError` | `IDEMPOTENCY_KEY_REQUIRED`, `INVALID_IDEMPOTENCY_KEY` |
| `409` | `Conflict` | `IDEMPOTENCY_KEY_REUSED` |
| `429` | `TooManyRequests` | `RATE_LIMITED` |
| `503` | `ServiceUnavailable` | `REQUEST_TIMEOUT`, `CATALOG_UNAVAILABLE`, `SERVICE_UNAVAILABLE` |

`Retry-After` ставить `errorHandler.js` з поля `retryAfter` помилки (`TooManyRequestsError`, `ServiceUnavailableError` у `service/errors.js`), тож сервіси не працюють із заголовками напряму.

## 3. Альтернативи

### Idempotency-Key необов'язковий — відхилено

Зворотно сумісно, але клієнт, який забув заголовок, знову отримує дублікати при ретраях. Клієнт у нас один і живе в тому самому репозиторії, тож обов'язковий ключ нікого не ламає.

### Ключі ідемпотентності в `Map` у пам'яті — відхилено

Простіше (так у прикладі Практики 5), але після перезапуску сервера ретрай створить дублікат, а `Map` росте без обмежень. Таблиця SQLite коштує один файл репозиторію.

### Дедуплікація за вмістом (та сама назва + автор + файл) — відхилено

Не відрізняє ретрай від свідомої повторної публікації і вимагає правил «що вважати однаковим» для кожного ресурсу. Ключ від клієнта однозначний.

### Готові бібліотеки (`express-rate-limit`, `connect-timeout`) — відхилено поки що

Поведінка потрібна мінімальна, а власні middleware на 20–30 рядків легко тестувати й одразу повертають наш `ErrorResponse`. Якщо знадобиться ковзне вікно чи спільне сховище лічильників, перейдемо на `express-rate-limit`.

### Circuit breaker — відкладено

Корисний для викликів зовнішніх сервісів. Зараз єдина залежність — локальна SQLite, а виклик AI API (`assistant`) з'явиться пізніше; тоді й додамо breaker навколо нього.

## 4. Наслідки

### Для розробки

- Ретрай `POST /materials` безпечний: дублікатів немає навіть після перезапуску сервера.
- Клієнт розрізняє «повтори пізніше» (`429`, `503` + `Retry-After`) і «виправ запит» (`4xx`) за статусом, не розбираючи текст.
- За `requestId` видно всі спроби однієї операції в логах.
- Кожен `POST /materials` потребує ключа: фронтенд генерує `crypto.randomUUID()` на кожну дію; тести передають ключ явно.
- Snapshot каталогу живе в пам'яті процесу і може бути застарілим — саме тому відповідь позначається `degraded: true`.
- Таблиця `idempotency_keys` росте; прострочені записи перезаписуються при повторному використанні ключа, а періодичне очищення (`DELETE … WHERE created_at < …`) додамо, коли з'являться фонові задачі.

### Для релізів

- Налаштування через env: `REQUEST_TIMEOUT_MS`, `RATE_LIMIT_MAX`, `RATE_LIMIT_WINDOW_MS`, `CHAOS`, `FAULT_ERROR_RATE` і `FAULT_DELAY_MS` (Практика 8, `docs/practice8/report.md`) (`backend/config.js`) — однаково для локального запуску і Docker.
- `GET /health` тепер повертає JSON і `503` у degraded-стані — готовий для Docker healthcheck (тиждень 6) і дашборда (тиждень 8).
- Лічильники rate limit і snapshot каталогу локальні для процесу: при горизонтальному масштабуванні їх доведеться винести.
